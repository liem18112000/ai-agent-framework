Evaluation spec · Agentic QA · test-plan generation

Measuring an agentic QA system, end to end

Three layers of metrics, a golden dataset schema, a weighted judge rubric, and the calibration protocol that keeps the judge honest.

The three-layer framework

A plan can look excellent and still catch no bugs — so measure the artifact, the process that produced it, and what it does in the field.

Layer 1 — Test plan quality the output

  • Requirement coverage — % of requirements with ≥1 mapped test case (traceability matrix)
  • Groundedness — no hallucinated features, endpoints, or preconditions
  • Precision & recall — against human-written reference plans in the golden set
  • Scenario depth — happy / edge / negative / boundary mix
  • Executability — clear steps, expected results, test data specified
  • Redundancy rate — near-duplicate cases via semantic clustering
  • Prioritization quality — rank correlation vs a QA lead's ordering

Layer 2 — Agent process how it got there

  • Tool call success rate, retries, error recovery
  • Latency and token cost per plan
  • Grounding rate — claims traceable to documents actually retrieved
  • Consistency — variance across N runs on the same input

Layer 3 — Downstream effectiveness the real signal

  • Defect detection rate — bugs found when the plan is executed, vs baseline
  • Mutation score — % of seeded bugs the plan's cases catch; closest thing to ground truth
  • Human acceptance — cases kept as-is vs edited vs deleted
  • Escaped defects — production bugs in areas the plan claimed to cover

Golden dataset schema

Each entry pairs one feature input with a human-authored reference plan. Start with 20–30 entries, stratified by difficulty and domain.

{
  "id": "golden-014",
  "input": {
    "feature_spec": "...",          // exactly what the agent receives
    "context_docs": ["api.md"],
    "constraints": "regression only"
  },
  "reference_plan": {
    "test_cases": [ { "case_id", "requirement_refs",
                      "type", "priority", "steps",
                      "expected", "tags" } ],
    "must_have_cases": ["TC-01", "TC-04"],   // recall measured here
    "nice_to_have_cases": ["TC-07"],
    "known_traps": [ "Agent tends to invent /v2 endpoint",
                     "Spec ambiguous on null handling" ]
  },
  "metadata": { "difficulty", "domain",
                 "author", "spec_ambiguity" }
}

Split must-have from nice-to-have

Recall on must-haves is the headline number. Counting every case equally rewards padding.

Include ambiguous specs on purpose

A good agent asks or flags assumptions; a bad one hallucinates. This is where agents differ most.

Encode known traps

Every hallucination pattern found in production becomes a regression check in a golden entry.

Match cases semantically

Pair agent cases to reference cases by embedding similarity or an LLM matcher — never by ID — then compute recall and precision on the pairs.

Judge rubric and scoring weights

Score each dimension 1–5 in a separate judge call — batching dimensions causes halo effects. Force evidence (quotes from the spec, or "NOT FOUND") before the score. Only three of six dimensions need the LLM judge; compute the rest deterministically.

Calibration protocol

Run this before trusting any judge score, and repeat it whenever the judge model or prompt changes.

  1. Two humans score ~30 plans on the same rubric, independently.
  2. Compute human–human agreement (Cohen's kappa). If humans disagree, fix the rubric wording — not the judge.
  3. Require judge–human kappa ≥ human–human kappa minus ~0.1.
  4. Pin the judge model version; re-calibrate on any change to model or prompt.

Canary plans

Keep a small set of deliberately bad plans — hallucinated features, missing negative tests — and score them every run. If the judge ever rates a canary above 3, the eval pipeline is broken, not the agent.
