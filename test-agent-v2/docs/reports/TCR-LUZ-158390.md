## 2. Test Summary

An automated **OpenAPI conformance suite** was generated from the live `luz_docs` contract and executed
against dev: **9 scenarios, 7 passed, 2 failed**, plus a 2-scenario `luz_docs_import` run (1 passed,
1 failed). The failures are **four genuine contract defects** (§8).

**This run does not test LUZ-158390.** The suite verifies that the services honour their published
OpenAPI contract; the story's 23 acceptance criteria describe ZIP-import *behaviour* (metadata pairing,
entry classification, UTF-8 titles, OS-artefact skipping). **22 of 23 ACs are uncovered** (§5). The
report is therefore evidence about contract health, **not** evidence that the story is done.

| D-4 | `GET /{tenant}/folders/{folder-id}` returns **404**, but the spec declares only **200/500** | Low | **Spec defect, not code** — behaviour is correct; the contract is stale |

**Residual risk:** the story's entire behaviour set is unverified. The known-missing implementation the
story itself documents (metadata pairing absent, `isExcludedFile` only skips dot-prefixed names) has no
covering test, so a regression there would be invisible.

---

## 9. Rationale for Key Decisions

- **Happy-path scenarios assert `expect_status=0`, not `200`.** The spec is the oracle — a guessed status
  can only re-state what the author already believed. This is what surfaced D-1…D-4.
- **Read-only GETs only.** Write probes against a shared dev tenant were deliberately not auto-generated.
- **D-4 is routed to the spec, not the code.** Both directions of contract drift are defects, but they
  are fixed in different places.

## 11. Lessons Learned

- A conformance suite is cheap and finds real defects, but it is **orthogonal to story acceptance** —
  reporting it as story coverage would have been misleading.
- Scenario→AC traceability needs **per-AC** ids; story-level `source_refs` cannot produce a per-AC matrix
  automatically (the matrix above was assembled by hand).
- Two defects in the reporting path itself were only exposed by running against real data (a mislabelled
  version, a misfiled triage bucket) — synthetic fixtures would not have caught either.

## 12. Conclusion and Recommendation

**Verdict: FAIL — cannot certify LUZ-158390.**

Not because the product failed: because **22 of 23 acceptance criteria have no covering test**. The
executed suite passed 8 of 11 scenarios and found 4 contract defects, none of which belong to this story.

**Recommendation — do not close LUZ-158390 on this evidence.** Required before re-reporting:
1. Build the `transfer.zip` fixture set named in the story's Test notes (valid/absent/unparseable/orphaned
   metadata, disallowed element, >100 KB, OS artefacts, nested folders, UTF-8).
2. Implement AC-derived scenarios with **per-AC** `source_refs`.
3. File D-1…D-4 separately; they are independent of this story.
