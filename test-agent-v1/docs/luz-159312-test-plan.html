Scope

In scope

  • Functional — main-flow + feature tickets: LUZ-159443, LUZ-159860, LUZ-159861, LUZ-159862, LUZ-159498
  • LUZ-156281 (parent) — full-depth coverage (happy + negative/boundary/error), not just regression — it's a core billing/compliance flow
  • Performance — the credit-only invoice-run operation, end-to-end through the real owned downstream services (AccountRestClient, AccountingGroupRestClient …)
  • Integration — real owned services (luz_finance / luz_docs / luz_jsonstore); third parties handled by those services in sandbox
  • Recorded PRs — inspect the 17 dev-panel PRs/commits to confirm they map to the scoped tickets; supporting evidence only, no new test targets

Out of scope

  • Enrichment (LUZ-Docs enricher trigger, enrichmentstatus) — a company-tenant concern, unrelated to this individual-client story. Removed entirely, incl. its API cases, Playwright smoke, and jsonstore dual-verification. Correction applied this session.
  • File-import concurrency — LUZ-158446 / LUZ-158390: not the performance target (the title is misleading); removed. Perf targets the credit-only operation, not file import.
  • Android dev testing — LUZ-158824 / LUZ-158241: separate, independently-scheduled QA track; non-blocking.
Two corrections drove this scope: (1) the performance work targets the credit-only billing operation processes, not file-import concurrency; (2) enrichment applies only to the company tenant, so it is entirely out of this individual-client plan.

Methodology & environment

Functional approach
End-to-end, flow-based — drive real controller chains (Accounting → Banking → Dunning) rather than isolated per-controller tests.
API / contract
API-level tests against owned endpoints as the primary regression gate for contract behaviour.
UI (Playwright)
Webclient v2.0 UI happy-path / reachability smoke only — advisory/parallel this cycle, not release-blocking (gating next cycle).
Third parties
Tests call the owned downstream services for real; those services handle card/notification/ePost calls internally in sandbox.
Safety
No real charges/notifications — enforced by sandbox config (test keys, isolated tenant) + a test-mode flag asserted in the response (trust-by-environment).
Performance bar
Pass = the invoice-run job completes and produces a job-report (processed/failed counts). No numeric SLA this cycle — "faster than before" is directional/informational.

Entry / exit criteria & risks

Entry criteria

  • Staging/sandbox env up with test API keys + an isolated test tenant (no live routing)
  • Owned downstream services (luz_finance / luz_docs / luz_jsonstore) deployed to staging
  • Test data: individual clients with valid + invalid cards, outstanding invoices, seed-able retry/dunning states
  • Recorded-PR inspection complete (the 17 dev-panel PRs mapped to scoped tickets)

Exit criteria & risks

  • Exit: all functional scenarios pass; PT-01 job completes with report; IT-01 confirms no real charges/notifications
  • Exit: negative/boundary/error cases green for the billing/compliance flows
  • Risk: sandbox uptime / rate limits can make runs slow or flaky; a failure may be ambiguous (our bug vs sandbox)
  • Risk: Playwright is advisory only — a red UI run does not gate release this cycle
